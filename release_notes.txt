### Payment, Notification & Asynchronous Communication

- Implemented the Payment Service with PostgreSQL and Kafka-based payment confirmation events.
- Integrated the Order Service with the Payment Service to process payments.
- Implemented the Notification Service using MongoDB, rabbitmq consumers, and email notifications.
- Added MailDev to Docker Compose to test and inspect outgoing emails.
- Explored Eventual Consistency and the Saga Pattern, handling order states (`PENDING`, `CONFIRMED`, and `CANCELLED`) based on payment results.
- Implemented compensating transactions to restore product stock when a payment fails.
- Added payment idempotency using a unique order reference to prevent duplicate payment processing.
- Integrated RabbitMQ to handle email jobs asynchronously using Direct Exchanges, Routing Keys, and durable queues.
- Implemented an email worker using `@RabbitListener` with manual acknowledgments (ACK/NACK).
- Configured message retries with TTL and Dead Letter Exchanges, routing messages to a Dead Letter Queue after the maximum number of attempts.


## Saga, Outbox, Kafka

**Saga**
- Problem: a process spans several services, and one step fails after others already succeeded. `@Transactional` can't roll back across services.
- Solution: run compensating actions (like a refund) to undo the earlier steps.

**Outbox**
- Problem: you save to the DB and publish an event, but one can succeed while the other fails. The event is lost, or it describes something that never happened.
- Solution: save the event in the same DB transaction as the data, then send it afterwards.

**Kafka**
- Problem: many consumers need the same events, and you want to avoid coupling, tracking delivery yourself, or losing history.
- Solution: producers publish once, each consumer tracks its own progress, and events are stored so they can be replayed, with ordering per key.

**Together**
- Saga coordinates the steps.
- Outbox makes sure the events are not lost.
- Kafka delivers them.
